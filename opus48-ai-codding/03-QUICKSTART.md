## 🚀 新手路径（按顺序）

### 第 1 天：理解理念

1. 先看 `examples/sample-project/` —— 理解完整应用
2. 读 `02-README.md` —— 了解设计理念

### 第 2–3 天：建立共识

1. 复制 `templates/CONTEXT.md.template` 到项目根目录
2. 用 `/grill-with-docs` 开始 —— 不用急着写代码
3. 参考 `examples/sample-project/` 里的写法

### 第 4–5 天：完整流程

1. 尝试 `/to-prd` → `/to-issues` → `/implement` 一条龙
2. 用 `templates/` 里的模板（推荐新格式：`single-issue.md.template`）

### 第 2 周：加入更多技能

1. 加入 `/codex-review` 预审代码
2. 加入 `/improve-architecture` 深化模块

### 第 1 个月：巡检

1. 跑一次 `/doc-rot` 巡检

1. 跑 `/doc-rot` 做一次完整巡检

3. 每月做一次 `/doc-rot`

## 🎯 新手第一天：试试这 3 个核心技能

### 1️⃣ /grill-with-docs —— 先理解再动手

下次有需求时，先别急着写代码，用这个技能提问：

- 我们解决什么问题？为谁解决？
- 核心概念是什么？确切含义？
- 边界在哪里？什么不做？
- 异常场景怎么处理？

把共识记在 CONTEXT.md。

### 2️⃣ /tdd —— 测试先行

写代码前，先写测试：

1. 🔴 写一个失败的测试（读起来像规格说明）
2. 🟢 写刚好让测试通过的代码（不要过度设计）
3. 🟠 重构（可选，改进设计保持绿色）
4. 重复，一次只写一个测试

### 3️⃣ /doc-rot —— 每月检查

月底时，花 15 分钟：

- 检查 CONTEXT.md 还对吗？
- API 文档和代码一致吗？
- 计算健康度评分

## 💡 常见问题

### Q：我不想一下子用所有 Skill，太复杂了

**A**：没问题！从这 3 个开始：
1. `/grill-with-docs`：先理解再动手
2. `/tdd`：测试先行
3. `/doc-rot`：每月检查文档

习惯了再加其他。

### Q：Grill 多久算够？什么时候可以写代码？

**A**：当你觉得：
- 概念清晰，没有歧义
- 边界明确，知道什么做什么不做
- 验收标准可验证

**不要追求完美**，80% 清楚就可以开始，剩下的边做边调整。

### Q：原型代码要保留吗？

**A**：不要！保留答案，丢弃脚手架。
- 原型是手电筒，照亮方向后就放下
- 把学到的记录到 CONTEXT.md 或 ADR
- 原型代码删除或明确标记为「不要用」

### Q：我知道模块可以变深，但现在没时间

**A**：没关系！用 `/improve-architecture` 把机会记录下来，以后再做。
- 每周留 1–2 小时做架构改进
- 不要追求完美，小步前进

### Q：Issue 用旧格式还是新格式？

**A**：推荐新格式（GitHub-style），但旧格式仍然支持：

- **新格式**：每个 issue 独立文件，有状态跟踪、TODO 关联、历史记录
- **旧格式**：所有 issue 在一个清单文件中，简单直接

建议：新项目用新格式，老项目可以继续用旧格式或逐步迁移。

### Q：什么时候需要创建 TODO？

**A**：当 issue 被某个问题阻塞时：
- 问题不明确，需要确认
- 依赖某个决策
- 不确定技术方案

把 TODO 记录在 `docs/todos/` 目录，明确标记它阻塞了哪些 issue。
