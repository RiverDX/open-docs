## 🎯 快速选择指南

### 按场景选择

| 你想做什么 | 用哪个 Skill | 怎么做 |
|-----------|-------------|-------|
| **有一堆 backlog 要整理** | `/triage` | 分类、打标签、标记 AFK/HITL |
| **有原型图+简要描述** | `/prototype-to-business` | 从原型图和描述生成业务梳理文档 |
| **理解代码生成文档** | `/grill-with-docs` | 先读取代码，然后询问概念，写入 CONTEXT.md |
| **根据简要需求生成 PRD** | `/grill-with-docs` → `/to-prd` | 先 Grill 澄清需求，再用已有共识生成 PRD |
| **根据 PRD 拆分任务** | `/to-issues` | 读取 PRD，拆成垂直切片的小 issue |
| **开始写代码实现** | `/implement` 或 `/tdd` | 一条龙用 `/implement`，分步走用 `/tdd` |
| **审查写完的代码** | `/codex-review` | 读取 diff 或改动的文件，按 6 维度检查 |
| **优化现有架构** | `/improve-architecture` | 找深模块机会，渐进式改进 |
| **需求不确定要探索** | `/prototype` | 做个小原型验证想法 |
| **会话太长要分流** | `/handoff` | 整理上下文，交给新会话 |
| **检查文档是否过期** | `/doc-rot` | 每月一次巡检 |

### 按阶段选择

```
想法阶段
   │
   ├─→ 有 backlog → /triage
   │
   ├─→ 有原型图 → /prototype-to-business
   │
   ├─→ 不清楚 → /grill-with-docs (必须先做！)
   │
   └─→ 要探索 → /prototype
        │
        ↓
需求固化阶段
   │
   ├─→ 共识已达成 → /to-prd
   │
   └─→ PRD 已写 → /to-issues
        │
        ↓
实现阶段
   │
   ├─→ 一条龙 → /implement
   │
   └─→ 分步走 → /tdd → /codex-review
        │
        ↓
优化阶段
   │
   ├─→ 改进架构 → /improve-architecture
   │
   └─→ 定期检查 → /doc-rot
```

### 1. `/triage` - 画布整理

**适用场景**：
- ✅ 有一堆 issue/idea 需要分类整理
- ✅ 不知道先做哪个，需要优先级排序
- ✅ 想区分哪些是 AI 能做的（AFK），哪些需要人（HITL）

**怎么使用**：
1. 输入：提供要整理的 issue 列表（链接或文本）
2. 步骤：
   - 扫：列出所有 issue
   - 分类：打标签（bug/enhancement/question/docs）
   - 定状态：标记 needs-triage/needs-info/ready-for-agent/ready-for-human/wontfix
   - 排序：建议执行顺序
3. 输出：Triage 报告 + 标签建议

**输入示例**：
```
我有这些 issue 要整理：
1. 用户登录后页面白屏
2. 加个导出 Excel 的功能
3. 这个 API 怎么用？
4. 更新一下 README
```

**输出示例**：
```
## 分流结果详情

| Issue | 标题 | 类别 | 状态 | AFK/HITL | 优先级 |
|-------|------|------|------|----------|--------|
| 1 | 用户登录后页面白屏 | bug | ready-for-human | HITL | P0 |
| 2 | 加个导出 Excel 的功能 | enhancement | ready-for-agent | AFK | P1 |
```

### 2. `/prototype-to-business` - 原型图转业务梳理

**适用场景**：
- ✅ **有原型图+简要描述**（新！）
- ✅ 需要从UI设计梳理业务流程
- ✅ 从原型图开始做需求分析

**怎么使用**：
1. 输入：原型图描述 + 简要描述
2. 步骤：
   - 理解输入：阅读原型图和描述
   - 识别用户角色：梳理涉及的用户角色
   - 梳理业务流程：画出正常和异常流程
   - 拆解功能清单：从原型图拆解功能点
   - 分析数据需求：识别核心实体和字段
   - 描述界面：描述页面元素和交互
   - 自查：检查输出质量
3. 输出：业务梳理文档

**输入示例**：
```
这是原型图和简要描述：

原型图：
[描述原型图，或提供图片链接]

简要描述：
[用户提供的简要描述]
```

### 3. `/grill-with-docs` - 对齐共识

**适用场景**：
- ✅ **理解代码生成文档**（最常用！）
- ✅ 需求不明确，概念有歧义
- ✅ 想建立团队共享语言
- ✅ 刚接手一个项目，想理解现有代码

**怎么使用**：
1. 输入：用户的想法描述 + 相关代码（如果有）
2. 步骤：
   - 扫：读取现有 CONTEXT.md 和代码
   - 问第一波：目标（我们解决什么？为谁？）
   - 问第二波：概念（这个叫什么？确切含义？）
   - 问第三波：边界（什么在范围内？什么不做？）
   - 记录：写入 CONTEXT.md
3. 输出：CONTEXT.md + Grill 报告

**输入示例（理解代码生成文档）**：
```
这是项目里的代码，帮我理解一下：
[读取 src/models/Task.js 的内容]
[读取 src/models/Order.js 的内容]
```

**输入示例（需求不明确）**：
```
我想做个任务管理工具，大概就是能创建任务、更新状态...
```

**AI 会这样问**：
```
让我先澄清几个问题：

## 目标层
1. 我们解决什么问题？是个人任务管理，还是团队协作？
2. 目标用户是谁？

## 概念层
1. 核心概念有哪些？（比如 Task/Status/Priority）
2. 你说的「状态」确切指什么？有哪些状态？

## 边界层
1. 什么在范围内？什么明确不做？
2. 要不要用户认证？要不要持久化？
```

**关键提示**：
- 不要跳过 Grill 直接写代码！
- Grill 越充分，后面返工越少
- 不确定的概念必须问清楚

### 4. `/handoff` - 上下文接力

**适用场景**：
- ✅ 当前会话超过 100K tokens（接近变笨区）
- ✅ 想把工作分给另一个 AI 处理
- ✅ 需要聚焦某个具体任务

**怎么使用**：
1. 输入：要接力的任务 + 相关上下文
2. 步骤：
   - 整理：把无关对话过滤掉
   - 总结：已达成的决策、未完成的任务
   - 引用：用文件路径代替重复内容
3. 输出：Handoff 摘要 + 下一步建议

**输入示例**：
```
我们刚才在做任务管理系统，现在要开始实现 Issue 1 了。
这个会话太长了，帮我 handoff 到新会话。
```

**输出示例**：
```
## Handoff 摘要

### 已完成
- ✅ Grill 完成，CONTEXT.md 已写
- ✅ PRD 完成
- ✅ Issues 已拆分

### 待完成
- 🔘 实现 Issue 1：用户可以创建任务并看到在列表中

### 关键文件
- CONTEXT.md（共享语言）
- docs/prd/task-management-2026-06-28.md（PRD）
- docs/issues/task-management-2026-06-28.md（Issues）

### 下一步
建议启动新会话，运行 `/implement` 开始实现 Issue 1
```

### 5. `/prototype` - 草稿探索

**适用场景**：
- ✅ 高保真问题（需要实际验证）
- ✅ UI 交互不确定，想做个原型
- ✅ 技术方案不确定，想先试试

**怎么使用**：
1. 输入：要验证的问题 + 约束条件
2. 步骤：
   - 明确：要回答什么核心问题？
   - 极简：做最小可用原型，不要过度设计
   - 验证：回答问题，然后丢弃原型
3. 输出：原型代码 + 验证结论

**输入示例**：
```
我不确定用 SQLite 还是 PostgreSQL 合适，帮我做个原型验证一下。
```

**关键提示**：
- 原型是手电筒，照亮方向后就放下
- 不要把原型代码变成生产代码
- 把结论写入 CONTEXT.md 或 ADR

### 6. `/to-prd` - 定稿草图

**适用场景**：
- ✅ **根据简要需求生成 PRD**（但必须先 Grill！）
- ✅ 共识已达成，需要固化成正式文档
- ✅ 需求清晰，想整理成用户故事

**怎么使用**：
1. 输入：CONTEXT.md + Grill 对话历史
2. 步骤：
   - 收集：读取已有共识，不要重新提问
   - 写问题陈述：我们解决什么？为谁？
   - 写用户故事：作为 [角色]，我可以 [动作]，以便 [价值]
   - 识别深模块：找简单接口隐藏复杂实现的机会
3. 输出：PRD 文档

**输入示例**：
```
我们刚才 Grill 完了，CONTEXT.md 在这里：
[读取 CONTEXT.md 的内容]

帮我生成 PRD。
```

**用户故事示例**：
```
## 用户故事

### 故事 1：作为用户，我可以创建任务，以便记录要做的事
**验收标准**：
- [ ] 可以只传标题创建任务
- [ ] 可以传可选的描述
- [ ] 任务状态默认是 todo

**不做**：
- 截止日期
- 标签
```

**关键提示**：
- 只用已有共识，不要重新 Grill 用户
- 不确定的标记为 `[待验证]`
- 必须包含验收标准（可验证，不是模糊的）

### 7. `/to-issues` - 垂直切片

**适用场景**：
- ✅ **根据 PRD 拆分任务**（最常用！）
- ✅ PRD 已写，需要拆成可执行的小 issue
- ✅ 想确保每个 issue 都能独立验证

**怎么使用**：
1. 输入：PRD 文档
2. 步骤：
   - 读取：理解用户故事和验收标准
   - 切垂直切片：每个 issue 都是端到端的完整故事
   - 曳光弹先行：第一个 issue 最小但完整
   - 标记 AFK/HITL：区分 AI 能做的和需要人的
   - **生成分离的 Issue 文件**（新格式）：创建 `docs/issues/{功能名}-{YYYY-MM-DD}/` 目录，每个 issue 独立文件 + README 总览
3. 输出：Issue 清单文档（旧格式）+ 分离的 Issue 文件（新格式）

**输入示例**：
```
PRD 在这里：
[读取 docs/prd/task-management-2026-06-28.md 的内容]

帮我拆成 issue。
```

**✅ 好的垂直切片**：
```
Issue 1：用户可以创建任务并看到在列表中
- 端到端：从输入 → 存储 → 显示
- 可独立验证
```

**❌ 坏的水平切片**（不要这样！）：
```
Issue 1：先做数据库层
Issue 2：再做 API 层
Issue 3：最后做前端
- 单独不能运行
- 集成风险大
```

**执行顺序示例**：
```
## 执行顺序（建议）

### 第 1 步：曳光弹
- Issue 1：用户可以创建任务并看到在列表中（HITL）← 先做这个！

### 第 2 步：核心功能
- Issue 2：用户可以更新任务状态（AFK）
- Issue 3：用户可以删除任务（AFK）

### 第 3 步：完善
- Issue 4：用户可以按优先级筛选（AFK）
```

**新格式：分离的 Issue 文件**：
```
docs/issues/task-management-2026-06-28/
├── README.md                 # 总览（状态看板 + 依赖图）
├── 001-创建任务并看到在列表中.md
├── 002-更新任务状态.md
├── 003-删除任务.md
└── 004-按优先级筛选任务.md
```

**单个 Issue 文件格式**（带 frontmatter）：
```markdown
---
title: "[Enhancement] 用户可以创建任务并看到在列表中"
labels: enhancement, HITL, P0, status/pending
assignees: ''
created: 2026-06-28
---

# Issue 001：用户可以创建任务并看到在列表中

> **状态**：🟣 pending
> **优先级**：P0
> **类型**：enhancement
> **AFK/HITL**：HITL
> **依赖**：无
> **阻塞的 TODO**：无
> **对应 PRD**：[任务管理系统](../prd/task-management-2026-06-28.md)

## 目标
用户可以创建任务（只传标题），然后在任务列表中看到它。

## 验收标准
- [ ] 调用 `createTask("买牛奶")` 可以创建任务
- [ ] 调用 `getTasks()` 可以看到刚创建的任务

## 相关文档
- [PRD](../prd/task-management-2026-06-28.md)
- [CONTEXT.md](../../CONTEXT.md)

---

## 历史记录
| 日期 | 状态变更 | 说明 |
|------|---------|------|
| 2026-06-28 | created → pending | Issue 创建 |
```

**TODO 跟踪**：
当某个 issue 被问题阻塞时，创建 TODO 文件：
```markdown
docs/todos/todo-2026-06-28-001-确定持久化方案.md
```
TODO 文件记录：
- 需要确认的问题
- 阻塞的 issue 列表
- 建议的解决方案

### 8. `/tdd` - 红→绿→重构循环

**适用场景**：
- ✅ 开始实现 issue，想保证代码质量
- ✅ 喜欢测试先行的工作方式
- ✅ 想让测试像规格说明一样

**怎么使用**：
1. 输入：Issue + 验收标准（可以是单个 Issue 文件路径）
2. 步骤：
   - **理解验收标准**：明确要做什么
   - **更新 Issue 状态**：如果输入是单个 Issue 文件，将状态从 `pending` 更新为 `in-progress`，添加历史记录
   - 🔴 红：先写一个失败的测试（只一个！）
   - 🟢 绿：写刚好让测试通过的代码（不要过度设计！）
   - 🟠 重构：改进设计，保持测试通过（可选）
   - 重复：下一个测试
   - **完成后更新状态**：将 Issue 状态从 `in-progress` 更新为 `done`
3. 输出：测试代码 + 实现代码 + TDD 报告

**输入示例**：
```
开始实现这个 Issue：
[读取 Issue 内容]
验收标准：...
```

**好的测试示例**：
```javascript
// 测试读起来像规格说明
test("用户可以创建任务", () => {
  // 给定
  const title = "买牛奶";

  // 当
  const task = createTask(title);

  // 那么
  expect(task.title).toBe("买牛奶");
  expect(task.status).toBe("todo");
});
```

**测试原则**：
1. ✅ 通过公开接口测试，不要测试私有方法
2. ✅ 测试读起来像规格说明
3. ✅ 一次只写一个测试
4. ✅ 覆盖正常路径 + 边界条件 + 异常

**不要做**：
```javascript
// ❌ 不好：测试私有方法
test("内部计算方法", () => {
  expect(obj._privateMethod()).toBe(...);
});
```

### 12. `/implement` - 实现一条龙（推荐！）

**适用场景**：
- ✅ **实现 + 审查一步到位**（最常用！）
- ✅ 想一条龙走完 TDD + 代码审查
- ✅ Issue 清晰，想快速实现

**怎么使用**：
1. 输入：Issue + 验收标准 + CONTEXT.md（可以是单个 Issue 文件路径）
2. 步骤：
   - 理解任务：读 issue 和验收标准
   - **更新 Issue 状态**：如果输入是单个 Issue 文件，将状态从 `pending` 更新为 `in-progress`，添加历史记录
   - TDD 循环：红→绿→重构，一次一个测试
   - 自动审查：按 6 维度检查代码
   - 写报告：记录 TDD 循环 + 审查结果
   - **完成后更新状态**：将 Issue 状态从 `in-progress` 更新为 `done`
3. 输出：测试代码 + 实现代码 + Implement 报告

**输入示例**：
```
实现这个 Issue，一条龙完成：
[读取 Issue 内容]

CONTEXT.md 在这里：
[读取 CONTEXT.md]
```

**报告示例**：
```
## 概览
- 实现目标：Issue 1 - 用户可以创建任务并看到在列表中
- TDD 循环数：5 个
- 测试用例数：8 个
- SEV-1 问题：0 条
- 状态：已完成

## TDD 循环记录

### 循环 1：创建任务（只传标题）
- 🔴 红：写测试，确认失败
- 🟢 绿：写最简单的代码
- 🟠 重构：不需要

## 代码审查结果

### SEV-1（必须修复）
无 ✅

### SEV-2（建议修复）
无 ✅
```

### 9. `/codex-review` - 画布审查

**适用场景**：
- ✅ 代码写完，提交 PR 前先预审
- ✅ 想检查明显的 bug 和问题
- ✅ 想确保代码符合项目约定

**怎么使用**：
1. 输入：变更的代码（diff 或文件）
2. 步骤：
   - 读上下文：读取 CONTEXT.md
   - 检查 6 维度：
     1. 违反约定？
     2. 明显的 bug？
     3. 测试覆盖？
     4. 设计/架构？
     5. 性能/资源？
     6. 可维护性？
   - 分级：SEV-1（必须修复）/ SEV-2（建议）/ SEV-3（可选）
3. 输出：审查报告

**输入示例**：
```
这是刚才写的代码，帮我审查一下：
[读取 src/models/Task.js 的内容]
[读取 src/models/Task.test.js 的内容]
```

**问题分级示例**：
```
## SEV-1（必须修复，不超过 5 条）
1. **SQL 注入风险**
   - 位置：src/db.js:42
   - 问题：直接拼接 SQL 字符串
   - 建议：使用参数化查询

## SEV-2（建议修复）
1. **命名可以更好**
   - 位置：src/models/Task.js:15
   - 问题：变量名叫 `data`，不够清晰
   - 建议：改成 `taskData`

## SEV-3（可选改进）
1. **可以加注释**
   - 位置：src/models/Task.js:28
   - 建议：解释一下状态机规则
```

### 10. `/improve-architecture` - 深化模块

**适用场景**：
- ✅ 功能完成，想优化架构
- ✅ 想把浅模块变成深模块
- ✅ 想渐进式改进（不要重写！）

**怎么使用**：
1. 输入：现有代码 + 项目上下文
2. 步骤：
   - 找深模块机会：简单接口 + 丰富实现
   - 评估风险：改动范围、对现有功能影响
   - 排序：按收益/成本排序
   - 让用户选：不要自己决定
3. 输出：架构改进建议清单

**输入示例**：
```
这个模块写得有点乱，帮我看看怎么改进：
```

## ❓ 常见问题解答

### Q：我可以跳过 Grill 直接写代码吗？

**A**：不推荐！充分的 Grill 能避免 80% 的返工。如果你觉得需求足够清晰，可以用 `/to-prd` 直接写，但建议至少过一遍 Grill 的问题。

---

### Q：什么时候用 `/implement`，什么时候用分开的 `/tdd` + `/codex-review`？

**A**：
- 简单任务、熟悉领域 → 用 `/implement` 一条龙
- 复杂任务、想更细致控制 → 分开用 `/tdd` + `/codex-review`
- 不确定 → 先用 `/implement`，有问题再分开

---

### Q：什么是垂直切片？怎么切？

**A**：垂直切片是端到端的完整故事，用户能看到完整功能。

**怎么切**：
- ✅ 好：「用户可以创建任务并看到在列表中」（从输入 → 存储 → 显示）
- ❌ 坏：「先做数据库层」「再做 API 层」

---

### Q：什么是深模块？怎么识别？

**A**：
- ✅ 深模块：简单接口 + 丰富实现（调用方不需要知道内部）
- ❌ 浅模块：复杂接口 + 简单实现（调用方需要知道所有细节）

**怎么识别**：
- 看调用方需要知道多少内部细节
- 能隐藏的都藏在模块里

---

### Q：我的会话超过 120K tokens 了怎么办？

**A**：立即用 `/handoff` 分流到新会话！
- 超过 120K tokens 就是变笨区了
- AI 会注意力分散、开始编造假想
- `/handoff` 会整理关键上下文，过滤掉无关对话

---

### Q：什么是 AFK/HITL？

**A**：
- **AFK**（Away From Keyboard）：Agent 可以自己做，不需要人盯着
  - 需求明确、验收标准清晰、有类似代码参考
- **HITL**（Human In The Loop）：需要人在关键节点做决策
  - 涉及设计、第一次做新功能、高风险

---

### Q：我不确定选哪个 skill 怎么办？

**A**：
1. 看本文档开头的「快速选择指南」
2. 看 `00-NAVIGATION.md` 的路由表
3. 还是不确定？从 `/grill-with-docs` 开始

---

### Q：Issue 用旧格式还是新格式？

**A**：推荐新格式（GitHub-style），但旧格式仍然支持：

- **新格式**：每个 issue 独立文件，有 frontmatter、状态跟踪、TODO 关联、历史记录
  - 文件：`docs/issues/{功能名}-{YYYY-MM-DD}/001-{标题}.md`
  - 总览：`docs/issues/{功能名}-{YYYY-MM-DD}/README.md`
- **旧格式**：所有 issue 在一个清单文件中，简单直接
  - 文件：`docs/issues/{功能名}-{YYYY-MM-DD}.md`

建议：新项目用新格式，老项目可以继续用旧格式或逐步迁移。

---

### Q：什么时候需要创建 TODO？

**A**：当 issue 被某个问题阻塞时：
- 问题不明确，需要确认
- 依赖某个决策
- 不确定技术方案

**怎么做**：
1. 创建 TODO 文件：`docs/todos/todo-{YYYY-MM-DD}-001-{标题}.md`
2. 记录：需要确认的问题、建议的解决方案
3. 关联：在 TODO 中标记阻塞的 issue
4. 在 Issue 中：标记「阻塞的 TODO」指向这个文件

---

### Q：Issue 状态有哪些？怎么更新？

**A**：
- 🟣 **pending**：待开始
- 🔵 **in-progress**：进行中（`/tdd` 或 `/implement` 开始时自动更新）
- 🚧 **blocked**：被阻塞（被 TODO 或其他 issue 阻塞）
- ✅ **done**：已完成（`/tdd` 或 `/implement` 完成时自动更新）

状态变更都要记录在 Issue 的「历史记录」表格中。
